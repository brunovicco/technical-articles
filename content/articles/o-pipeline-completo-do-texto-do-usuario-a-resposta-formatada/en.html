Over the past few months, I have published separate posts about each component of the e-commerce conversational assistant: episodic memory, routers, DSPy, anaphora, Redis Stack, guardrails, observability, and QueryBuilder.

This post closes the loop by showing the complete path of a query: from the text the user types to the response they receive, passing through each component in its execution order.

Once again, I will use the e-commerce domain as an example. The architecture is the same one I have documented throughout the series.

The subgraph starts with setup_node. Using asyncio.gather, it loads everything the subgraph will need in parallel:

In a sequential system, these two calls would take ~300ms each. In parallel, they take as long as the slower call: ~320ms at P50.

The graph state leaves setup with user_preferences, browsing_history_summary, and account_context populated. If the client has bought sneakers before, that is in the context when the LLM generates the response.

Latency for this step: ~320ms.

Step 3 — Router node: anaphora + DSPy

router_node is where the cognitive decision happens. But before reaching DSPy, the anaphora resolver checks whether the message has implicit references:

"men's Nike sneakers up to R$300 with free shipping and good ratings" has no pronouns and no implicit continuation. The resolver does not modify the message.

If the user had said "and this one with free shipping?", the resolver would have expanded it to "and the Women's Nike Air Force 1 with free shipping?" before passing it to DSPy.

The complete trace

What each component decided

  • The semantic router decided it was a catalog search, without an LLM, in 35ms.

  • The anaphora resolver decided the message had no implicit reference in <1ms.

  • The DSPy router decided the scope, tool, and 8 filter parameters in 2.1s.

  • The QueryBuilder transformed those parameters into a safe FT.SEARCH query in <1ms.

  • The Redis Stack executed the search and returned 5 fields × 8 products in 45ms.

  • The DSPy Refine generated the response, detected a violation, and corrected itself in 3.6s.

  • The critique_node confirmed that nothing slipped through in 5ms.

Each component has a single responsibility; none knows what the previous one did. The graph architecture ensures that they connect through state.

What cost the most, and where there is room for improvement

DSPy dominates latency: 2.1s in the router + 3.6s in generate = 5.7s out of 6.1s total.

The DSPy router can only be accelerated with a faster model or the pagination fast path, which bypasses DSPy completely when the user asks for "more" results. Generate can be accelerated by reducing Refine's regeneration rate: if the Signature is more explicit about the opinion rule, the first attempt passes, saving ~1.8s.

Redis Stack is irrelevant to total latency: 45ms to search and return 8 paginated documents. This is where Fat/Slim/Hybrid modeling paid back its construction cost.
