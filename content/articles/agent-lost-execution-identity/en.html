After examining state and continuity in the first part of this series, one of the most frequent causes of strange behavior deserves separate attention: identity. In a stateful system, a request continues the previous story only if the components involved can associate it with the same conversation, the same logical execution, and, when delegation occurs, the same remote work.

When this fails, the effect for the application's user looks very much like memory loss. The agent asks again about something already answered, ignores a previous approval, repeats an analysis, or begins a new reasoning sequence. Before increasing context, changing models, or adding a memory layer, it is worth checking whether the runtime received the correct identifiers.

Conversation, execution, and delegation have different lifetimes

I distinguish three basic levels:

  • conversation_id represents the logical continuity of an interaction or process.

  • execution_id identifies a concrete attempt to process something within that conversation.

  • delegation_id identifies work handed to a specific capability, agent, or service.

This separation becomes especially useful when retries are involved. A transport timeout should not accidentally turn a repeat of the same delegation into new business work. At the same time, a new user request may belong to the same conversation and generate a different execution. Without this vocabulary, IDs end up being reused or recreated arbitrarily.

Automatic IDs are great at the start and dangerous when they become an implicit contract

During a prototype, letting each library create identifiers reduces code and speeds up the first version. The problem appears when that implementation starts receiving retries, different workers, queues, or remote calls. One service creates the session, another creates the run, the gateway adds a request ID, and telemetry generates a trace. After a few months, nobody can say confidently which identifiers represent the same unit of work.

A recovery test worth more than many happy-path tests

One simple way to validate this architecture is to trigger failure at the most uncomfortable point: after the specialist completes the task and before the orchestrator advances the next checkpoint.

If the implementation handles that delegation idempotently, the specialist call count remains one. When it rises to two, the test has revealed that some boundary lost the identity or result of the previous operation.

This is one reason why, on hearing that an agent “forgot” a conversation, I now start with the request path: which conversation_id arrived, which thread_id was used, which session_id was reopened, which execution was underway, and which delegation was resumed. In many cases, the model never lost the context; the application simply stopped pointing to the same persisted state.
