In the posts about Redis Stack, I showed the Fat/Slim/Hybrid model and how the modeling decision directly affects what the LLM receives. Today I want to show the layer between DSPy's RouterOutput and Redis: the QueryBuilder.

It is the component that turns a Pydantic object containing semantic filters into a valid, safe, and correct FT.SEARCH string. It sounds trivial, but it is not.

The problem with building FT.SEARCH queries manually

The first version of the search code built the query as an f-string:

Three immediate problems:

  • Special characters silently break the parser: RediSearch has 28 special characters in TAG fields that need to be escaped with a backslash. A product name such as "Nike Air (Plus)" without escaping becomes @nome:{Nike Air (Plus)}, which RediSearch parses as a malformed group of alternatives. The result: zero results, without an error.

  • Booleans do not exist in RediSearch: there is no native boolean field type. Fields such as frete_gratis and em_estoque need to be stored and queried as TAG fields with the string "true"/"false". If upstream sends True, 1, "sim", or "TRUE", the query needs to normalize them first.

  • LLM input cannot be trusted: DSPy returns text_search="Nike Air Max 270". This needs to become a tokenized fuzzy query, not a literal substitution; otherwise, you either search too narrowly (zero results for misspellings) or too loosely (irrelevant results).

TAG escaping: 28 special characters

RediSearch has a list of special characters that must be escaped in TAG field values. Most examples online only escape the obvious ones (-, .). In practice, product names contain (, ), +, &, /, and others.

The bug: "Nike & Co." without escaping becomes @marca:{Nike & Co.}. RediSearch interprets "&" as an AND operator within the TAG group and parses it as @marca:{Nike} AND @marca:{Co.}, which obviously returns zero results, without an error message or an exception.

Booleans as TAGs: the normalization upstream does not do for you

It is simple: the problem lies in normalization before reaching this point. Catalog APIs return True, 1, "sim", "TRUE", and "yes" for the same field. Pydantic with a validator solves this:

Without this validator, a field frete_gratis="TRUE" would pass through Pydantic as a string and reach _format_tag_boolean as a truthy value, generating @frete_gratis:{True} (with an uppercase T), which does not match an index storing "true" (lowercase), and returns zero results, without an error.

Fuzzy matching with tokenization rules

Sanitization: RediSearch injection is real

The LLM can (and eventually will) return text containing RediSearch commands. text_search="tênis LIMIT 0 1000 SORTBY preco" does not raise an exception; it simply executes.

The fallback is "*", a wildcard search that returns all documents in the index. It is fail-open: you deliver a generic answer instead of executing an injected command. In contexts where fail-closed would be more appropriate, the function can raise an exception instead of returning "*".
